# SuzuPay Master Strategy


> Last updated: 2026-09-19  
> This document is the strategic source of truth for SuzuPay.  
> It consolidates current project discussions, meeting notes, and historical strategy explored around SuzuPay.


## 0. How to read this document


SuzuPay has evolved materially over time. To avoid mixing old assumptions with current decisions, items are labeled as follows:


- **CURRENT** — current strategic direction or active project scope
- **IN PROGRESS** — currently being built, tested, negotiated, or prepared
- **IMPLEMENTED** — confirmed as already implemented or substantially completed
- **PLANNED** — intended next step with relatively high confidence
- **PROPOSED** — strategic hypothesis that still requires validation
- **HISTORICAL** — earlier strategy, target, or assumption retained for context
- **UNKNOWN** — requires confirmation before being treated as fact


The central strategic shift is:


**Stablecoin QR payment app → inbound traveler × local merchant × local operator platform → regional economic infrastructure / regional operating system**

# 1. Strategic thesis


## 1.1 Core idea


**CURRENT**


SuzuPay should not be understood only as a payment product.


The larger opportunity is to connect:


- overseas visitors
- digital nomads
- local merchants
- accommodations
- tourism operators
- DMOs
- municipalities
- regional communities
- payment and settlement rails
- local discovery and mobility
- incentives and campaigns
- behavioral / transaction data


into one regional economic loop.


The user journey is:


**Discover → Visit → Stay → Participate → Pay → Circulate → Return**


Payment is the high-frequency transaction layer, but the broader product should own more of the visitor-to-region journey.


## 1.2 Why this matters


Local tourism and inbound projects are typically fragmented across:


- tourism websites
- maps
- coupons
- reservation tools
- payment providers
- local point programs
- LINE accounts
- merchant operations
- DMO / municipality projects
- one-off subsidy projects


SuzuPay's opportunity is to connect these fragmented layers so that the region can both improve the visitor experience and retain data / relationships after the transaction.


## 1.3 Strategic flywheel


**CURRENT / PROPOSED**


1. Visitors receive useful discovery, access, incentives, or payment utility.
2. Merchants adopt because the operational burden is low and customer acquisition improves.
3. Usage naturally generates transaction, visit, campaign, and behavioral data.
4. Regions can use the data to improve circulation, campaigns, merchant support, and visitor distribution.
5. Better regional experiences and incentives increase future usage.
6. The same operating model can be replicated across other regions.


A guiding principle is:


**Make the useful action itself generate the data needed for the next improvement.**

**PROPOSED**

- regional heat maps
- area circulation metrics
- merchant performance
- visitor segment analysis
- export / reporting
- subsidy / public project reporting

- LINE and external CRM integration


This layer is a major path from a consumer/payment product to a B2B/B2G regional infrastructure product.


## 2.4 Layer D — Payment and settlement


### Historical origin


**HISTORICAL**


The original SuzuPay concept was:


- Solana-based QR payment
- visitors holding USDC / USDT
- conversion into SuzuPoints
- merchant QR payment
- merchant receives JPY settlement
- low-cost, fast stablecoin settlement
- user FX / conversion fee plus merchant fee


Historical fee assumptions included:


- user FX / conversion: around 1%
- merchant fee: around 0.5%, potentially around 0.3% at scale


These figures are **not automatically current commercial terms** and must be reconfirmed before external use.


### Strategic moat


**CURRENT / PROPOSED**


The defensible payment value is not simply on-chain P2P transfer.


The harder and more valuable layer is:


- regulated JPY off-ramp
- merchant settlement
- AML / KYC
- travel rule and risk controls where applicable
- merchant accounts
- banking integration
- stablecoin liquidity
- operational reconciliation
- compliant regional merchant acceptance


The long-term ambition is closer to a **Web3-native regional PayPay / merchant network** than a pure wallet-to-wallet transfer app.

# 6. AI / LocalManus / OpenClaw strategy


## 6.1 Goal


**CURRENT / PROPOSED**


Use AI agents to make regional portal creation and maintenance economically scalable.


The target workflow is:


**Research → source verification → structured regional data → page generation → QA → preview deploy → publish → monitor → refresh**


## 6.2 LocalManus-style operating model


The system should be capable of:


- researching candidate regions
- identifying high-value local information
- collecting official and reliable sources
- structuring entities and attributes
- generating region-specific portals
- updating stale information
- managing many regional sites / accounts centrally
- creating preview deployments
- monitoring broken or stale pages
- proposing content and campaign updates


## 6.3 OpenClaw / Grokbot role


**PROPOSED**


OpenClaw or an equivalent local agent environment can act as the operational layer that:


- reads SuzuPay project knowledge
- inspects code and documents
- invokes research workers
- invokes site-generation workers
- creates branches / PRs
- deploys previews
- performs read-only monitoring
- coordinates repeatable regional production


A useful artifact-state classification is:


**FACT / IMPLEMENTED / IN PROGRESS / PLANNED / PROPOSED / UNKNOWN**


Agents should avoid silently converting an idea into an implementation fact.


## 6.4 Why AI matters strategically


Tourism information changes slowly enough that conventional sites often become stale, but frequently enough that manual maintenance across many regions becomes expensive.


AI-assisted maintenance can make a many-region strategy feasible if:


- source provenance is preserved
- updates are reviewable
- confidence / freshness is tracked
- local operators can override AI
- generated pages share one structured data model

# 16. Strategic risks


Major risks to manage explicitly:


1. **Regulation / settlement risk** — payment and stablecoin flows may require licenses, partners, or architecture changes.
2. **Cold-start merchant network** — consumer utility is weak without merchant coverage.
3. **Fragmented regional procurement** — public-sector sales can be slow and project-specific.
4. **Subsidy dependency** — grants should accelerate a repeatable business, not define the product.
5. **Portal commoditization** — content alone is easy to copy; differentiation comes from structured data + action + payment + regional operations.
6. **Stale data** — AI generation without provenance and freshness control destroys trust.
7. **Overbuilding Web3** — blockchain, DID, VC, or x402 should only be used where they improve the experience or economics.
8. **Strategy sprawl** — payment, tourism, portals, AI agents, and public projects must remain connected to one core regional operating thesis.


---


# 17. Decision filter


New ideas should pass the following questions:


1. Does this improve the visitor's ability to discover, access, participate in, or pay within a region?
2. Does it make merchant adoption or operation easier?
3. Does it increase measurable value for the region / operator?
4. Does usage create reusable regional data?
5. Can the capability be reused across many regions?
6. Does it strengthen SuzuPay's transaction / relationship / trust layer?
7. Is it meaningfully differentiated from a normal tourism website, payment app, or generic AI wrapper?


If the answer is mostly no, it is likely outside the core.

# 19. Portal network / site-factory strategy


## 19.1 From one portal to a distributed regional network


**CURRENT / PROPOSED**


The portal strategy should not stop at building one SuzuPay tourism website.


The larger opportunity is to build a **network of narrowly focused regional portals** around places where there is already a strong source of value, identity, demand, or under-discovered local activity.


Examples of "value sources" include:


- distinctive local industries
- pilgrimage / cultural routes
- traditional communities
- special local products
- remote-work / digital-nomad suitability
- unique experiences
- under-visited destinations near overcrowded hotspots
- regional communities with strong identity but weak digital discovery
- public programs seeking relationship population / repeat visitors
- places where inbound demand exists but information is fragmented


The strategy is:


**Find value source → structure regional knowledge → launch focused portal → acquire visitors → connect local merchants / experiences → attach SuzuPay actions → accumulate regional data → replicate**


This changes the portal from "content marketing" into **regional distribution infrastructure**.


## 19.2 Site portfolio model


**PROPOSED**


Instead of forcing every region into one giant national site, SuzuPay can operate a portfolio of focused sites with shared infrastructure.


A useful model is:


- one shared data model
- one shared design / component system
- one shared analytics layer
- one shared merchant / offer model
- one shared SuzuPay action layer
- many region- or theme-specific frontends


This makes it possible to optimize each site for its target audience while keeping operations centralized.


Potential themes include:


- digital nomad Japan
- relationship-population / repeat-visitor programs
- pilgrimage / cultural travel
- local food / producer discovery
- under-visited destinations
- workcation
- regional community participation
- specific subsidy / public-program use cases


The "furusato resident"-style concept is useful as a reference for how a focused user need can become the front door to a larger regional relationship.


## 19.3 Discovery of candidate regions


**CURRENT / PROPOSED**


AI research systems such as Jev or equivalent research agents should help continuously generate and rank candidate regions.


Candidate selection should consider:


- uniqueness of the underlying value source
- inbound / domestic demand potential
- availability and quality of source information
- local merchant density
- local operating partner availability
- DMO / municipality motivation
- overtourism / circulation need
- public-funding fit
- SuzuPay payment / incentive fit
- repeatability into other regions


The output should be a living **regional opportunity pipeline**, not a one-time research report.


## 19.4 Reference pattern: overtourism / public-information portals


**CURRENT**


Public-sector portal patterns such as overtourism countermeasure sites are strategically useful because they show how policy information, regional examples, and implementation guidance can be structured.


Read them in two buckets (see [`overtourism-cases.md`](overtourism-cases.md)):


1. **Proven / evaluated** — e.g. Miyajima stamp dispersal, Kyoto traffic + citizen portal, Otaru flow+logistics, Biei farmland conflict, Kamakura failed photo-spot experiment
2. **FY2026 newly selected** — ambitious proposals (baggage handoff, pre-demand control, night dispersal, etc.) that are not yet outcome-proven


The capability stack that matters for SuzuPay:


```text
show crowding → predict → recommend another place/time → change behavior with points/experience/transport/logistics → return value visibility to residents
```


SuzuPay should borrow the clarity and credibility of those sites, then add layers that ordinary public information portals often lack:


- actionable merchant / place discovery
- live regional data
- incentives
- payments
- visitor circulation
- operator dashboards
- measurable outcomes
- automated maintenance


The goal is therefore **not to clone a government portal**, but to turn the same information architecture into an operational product. The inbound prototype in `portal/` is the visitor-facing expression of that rule.

**2. Turn the implementation into reusable primitives**  
**3. Automate the expensive manual operations with AI**  
**4. Launch adjacent portals / regions from the same core**  
**5. Connect discovery to payment and measurable circulation**  
**6. Build a cross-region network**


This sequence is important: SuzuPay should avoid building a huge abstract platform before one or two regional operating models are proven.
